# Gem Horizon rollout

This change does not clear, retry, or move existing jobs. Preserve `REDIS_PREFIX`, `REDIS_DB`, and `REDIS_CACHE_DB`; changing them strands existing jobs. Horizon metadata uses `HORIZON_PREFIX=gem_horizon:`. Set `QUEUE_CONNECTION=redis`, Redis credentials/host/client, and persistent `CACHE_DRIVER=redis` in Forge. Require PHP Redis/Predis, pcntl and posix.

## First activation

1. Review live commit against the release before deploying. The audited live commit e2ecc10 trails main d5788ac; their diff includes Composer/frontend dependency lock changes, but no migrations. Back up any untracked server lockfiles/configuration. Do not silently overwrite them.
2. Before code activation, pause intake of imports and gracefully stop the old default and species-image workers using Forge. Allow existing jobs to finish; use stop wait at least 3750 seconds. Do not run old and new daemons simultaneously. Record pending/reserved/delayed counts without logging job payloads.
3. Deploy the reviewed commit and dependencies; rebuild config with `GEM_DEPLOY_REVISION="$(git rev-parse HEAD)" php artisan optimize` after the environment changes. The old default queue remains readable, with its own legacy supervisor, a 3660-second supervisor timeout, and 3700-second reservation. Previously queued import payloads can retain their 3600-second timeout.
4. Create exactly one managed Forge daemon: `/usr/bin/php8.3 /home/gemreptiles/gemreptiles.com/artisan horizon` (confirm installed PHP and actual application path). Working directory is that application. Run as the site user. Use autostart and autorestart, `stopasgroup=true`, `killasgroup=true`, `stopsignal=TERM`, and `stopwaitsecs=3750`. Start the daemon.
5. Run `php artisan queue:verify-horizon --wait=3750`. This verifies local running masters, all configured workers, and harmless probes returning the cached release revision on default, short, mail, imports, species-images, and species-bios. It fails closed. Check pending/reserved/delayed counts again and a real mail delivery separately. Probes contain random identifiers only; no customer payloads.
6. Confirm Forge scheduler runs every minute. `horizon:snapshot` runs every five minutes. Horizon dashboard requires login and admin status.
7. Replace the Forge deployment script with the reviewed `scripts/forge-deploy.sh` only after first activation. Forge deploy has a ten-minute budget. The hook waits at most 90 seconds for restart verification and fails without force-killing jobs if a long import is still draining. Before releases, pause import intake and drain long work outside the deployment window. Subsequent releases use `queue:verify-horizon --restart --wait=90`: old local master PIDs must exit, replacements must advertise all queues, and each queue must process a probe returning the expected full commit hash from its booted config. A successful terminate command alone never counts as success.

## Capacity and timing

Five fixed worker processes: legacy default (256 MiB), short/mail (128 MiB), imports (256 MiB), images (192 MiB), bios (128 MiB). Horizon master limit 64 MiB. These are worker recycling limits, not OS reservations or hard memory caps; budget all three apps plus PHP-FPM/database/Redis together before activation. Background workers have lower CPU priority. Scheduled and admin imports use the same unique job; a shared persistent Redis cache owns their two-hour uniqueness lock. New imports use `redis-imports` / `imports`, timeout 3600, reservation 3700. Images/bios use `redis-short`, job timeout120, supervisor150, reservation180. Mail/short supervisor90, reservation180. Separate queues retain separate capacity from imports. Legacy default stays available until old payloads are gone; only then consider removing it in a later reviewed change.

## Rollback

Pause new dispatch, gracefully stop Horizon (wait up to 3750 seconds), then deploy the previous reviewed release. Restore compatible queue workers for **all** queue names, including new `mail`, `imports`, and `short`; configure matching short/long reservations. The previous code does not contain `QueueHealthProbe`: finish queued verification probes before reverting code, or retain that class for the drain. Never clear queues as rollback. Preserve all Redis prefixes/DBs and retained job classes. Return traffic after worker processing is verified.
